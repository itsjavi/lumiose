## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by Halo and Nova in M12 (2026-10-15): @lumiose/vite skips every package in node_modules, so an npm-installed @lumiose/ui is not compiled: its .tsx components, ?client scripts (decision-63), islands and .stsx styles are not processed. Compile Lumiose-authored packages from node_modules: either the packages ship compiled output (decide which, record the reason), or @lumiose/vite includes packages that declare themselves Lumiose packages (for example a package.json field) in its compile and scan.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Photon (session photon-20261015T-m12b, branch claude/photon-m12b-fb2c94) claimed it.

Approach (AC #2), chosen by Photon on 2026-10-15: @lumiose/vite compiles and scans Lumiose packages installed in node_modules; packages keep shipping sources.

Why not compiled output:
- The compiled code depends on the target (server or client) and on the app's options (CSP mode, dev HMR and inspector hooks, browser targets), so a package would ship several builds and still miss the app's options.
- It ties the package to the compiled helpers of one lumiose version (TASK-353 chose sources for that reason).
- Scope tokens and island refs would be frozen at pack time, and the `?client` scan, the CSS manifest and the island manifest would still need the package's modules.
- Dev and build parity: the same sources go through the same compiler in both, as for the app's own modules and linked workspace packages.

Why the dependency rule instead of a new package.json field:
- A package that lists `lumiose` in its dependencies or peerDependencies is already the definition of a Lumiose package for linked workspace packages (TASK-74). Installed packages now follow the same rule, so a workspace link and an npm install behave alike, and third-party component libraries need no extra field.
- Those packages need Lumiose's handling anyway, also when they ship plain JS (@lumiose/query): in SSR they must be bundled with the app (`resolve.noExternal`) to share its `lumiose` instance, and the dep optimizer must leave them alone (`optimizeDeps.exclude`), since it would compile their `.tsx` with React's JSX transform.
- Scan speed: the crawl already reads the manifest of every dependency of the root. It now also walks the files of each installed Lumiose package (`dist/` included, nested `node_modules` excluded); Lumiose's own tooling (CLI, adapters, editor plugins) is skipped by name.
- Alternative kept for review: an explicit opt-in field (Svelte's `"svelte"` field or Solid's `"solid"` export condition). It would still need the dependency rule for SSR and the optimizer, and linked packages work without it.

Plan:
1. packages.ts: list installed Lumiose packages too; `owner(file)` for the exclude rule; skip Lumiose's own tooling.
2. Default `exclude`: node_modules except Lumiose packages (an explicit `exclude` replaces it). Transform, scan, HMR checks use it.
3. Server environments: `resolve.noExternal` and every environment's `optimizeDeps.exclude` get the Lumiose packages.
4. scan.ts: installed packages scanned whole (dist/ included).
5. Module ids: a package inside the root (node_modules) is named package-relatively (the innermost of root and package wins), in the compiler and in states.ts, so island refs and scope tokens never hold `/node_modules/.pnpm/...` paths.
6. Pack smoke (scripts/pack.ts --smoke): add the packed @lumiose/ui to the created app with a server-rendered Dialog page and an island, and check in Chromium under `lumiose dev` and `lumiose build` + `preview`: renders, hydrates, loads the ?client script.

Done (Photon, 2026-10-15):
- packages/vite: `Packages.lumiose()` lists linked and installed Lumiose packages (packages.ts); the default `exclude` is node_modules except their modules; the scan walks installed packages whole (`dist/` included, nested node_modules excluded); server environments get them in `resolve.noExternal`, every environment in `optimizeDeps.exclude`; Lumiose's own tooling (adapters, editor plugins, create-lumiose) is skipped by name.
- Dev: modules of installed packages may carry Vite's `?v=<hash>` (inherited from a versioned `.ts` importer); the default `include` accepts it, else Vite's OXC compiled them as React JSX.
- Compiler (module_id.rs) and states.ts: the innermost of root and package names a module, so a package under the root's node_modules gets `@lumiose/ui/dist/...` ids, not `/node_modules/.pnpm/...`.
- Pack test (AC #3): `pnpm pack:check --smoke` adds the packed @lumiose/ui (packed there while it is private, TASK-389) and scripts/fixtures/pack-ui to the create-lumiose app, then runs its Playwright test in Chromium under `lumiose dev` and `lumiose build` + `preview`: server HTML has the dialogs, Dialog's client script loads and marks a nested dialog (`data-nested-dialog-open`), an island's signal follows the dialog (hydrated), no page errors. CI's pack job installs Chromium (ui-e2e's Playwright version, cached).
- Negative check: the same app with `exclude: /node_modules/` (the old default) fails `lumiose build` (Rolldown: `react/jsx-runtime` from @lumiose/ui's dialog.tsx).
- Docs: reference/vite.md (`exclude` default, new "Lumiose packages" section with publishing advice for component libraries), concepts/islands.md, concepts/compiler.md; llms-full.txt regenerated.

For the user's review (DX, not new names):

- The `exclude` option's default changes from "anything in node_modules" to "node_modules except the Lumiose packages installed there"; an explicit `exclude` replaces the whole rule.
- Docs term "Lumiose packages" (reference/vite.md#lumiose-packages).
